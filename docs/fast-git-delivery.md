# PRHM — Fast Git Delivery (default workflow)

این دستورالعمل برای **تمام پروژه‌های PRHM** است؛ هدف، خاتمه‌دادن به چرخهٔ تکراری Bootstrap / Host Action / PR برای تغییرات عادی کد است.

## مسیر پیش‌فرض (بدون درخواست تأیید زیرساختی)

1. مخزن و شاخهٔ درست پروژه را شناسایی و سطح دسترسی **GitHub write** را بررسی کن.
2. تغییر کد/مستندات/asset را **مستقیماً با GitHub connector/API** در Git ثبت کن. برای فایل موجود از blob SHA جاری استفاده کن؛ برای چند فایل مرتبط، یک commit اتمیک با tree بساز. هیچ تغییری مستقیم روی Production ایجاد نکن.
3. اگر branch protection اجازه می‌دهد و تغییر کم‌ریسک است، commit را مستقیماً روی شاخهٔ مجاز بگذار. اگر شاخه محافظت شده یا تغییر پرریسک است، شاخهٔ مجزا و PR بساز؛ نه به عنوان راه‌حل پیش‌فرض برای ایراد ابزارها.
4. تست/CI متناسب با تغییر را روی **همان commit SHA** کنترل کن و نتیجه را گزارش بده.
5. اگر درخواست فقط «ثبت در Git» است، **اینجا تمام است**. بدون deploy، بدون Host Action و بدون Level-4.

## انتشار مستقل است

- **Git DONE**: repo + branch + full commit SHA + فهرست فایل‌های تغییریافته + وضعیت CI مشخص باشند.
- **LIVE DONE**: علاوه بر Git DONE، deploy از همان SHA با کنترل سطح دسترسی موجود، health check، گزارش مقصد/زمان/نتیجه و امکان rollback معتبر است.
- برای انتشار Production تأیید متناسب با سیاست ریسک پروژه لازم است (مثلاً Level-3 یا Level-4 برای اقدامات بحرانی)؛ این تأیید را نباید به «نوشتن فایل در Git» تعمیم داد.
- تغییرات امنیتی زیرساخت، توکن‌ها، کلیدها، سیاست‌های دسترسی، schema و پایگاه‌داده از مسیر تغییر کد کم‌ریسک **مستثنا** هستند.
- هیچ مسیر سریعی اجازهٔ commit کردن secret، دور زدن branch protection یا direct-edit Production ندارد.

## رفع بن‌بست و پیشگیری از کار تکراری

- اگر Agent MCP یک اکشن host-level یا bootstrap-level را در اختیار ندارد، برای **Git-only** اصلاً از آن استفاده نکن؛ از GitHub connector/API موجود استفاده کن.
- اگر GitHub write به دلیل مجوز/خطای شبکه ناموفق بود، علت واقعی را گزارش بده؛ PRهای تکراری و درخواست‌های Level-4 جایگزین رفع دسترسی GitHub نیستند.
- قبل از هر push، اختلافات محلی و فایل‌های ناشناخته را بررسی کن؛ هیچ worktree دارای تغییرات نامرتبط را به‌صورت کلی stage/commit نکن.
- عملیات شناسه‌دار یک‌بارمصرف را replay نکن.
- اگر آزمون CI موجود نیست، صریحاً «CI اجرا نشد» بنویس؛ آن را PASS فرض نکن.
- در هر درخواست یک بار تلاش منسجم و گزارش قابل‌بستن بده؛ برای گام‌های روتین، درخواست تأیید متوالی نکن.

## مسیر نمونه در ابزارهای فعلی

`GitHub get_repo` → `fetch_file` → `create_file/update_file` (یا Git tree commit چندفایلی) → `get_commit_combined_status`.

مسیر جایگزین برای فایل‌های **محیط توسعه**: Agent 3 `fast_dev_apply_v1` (فقط هدف مجاز و خارج از Production) + `project_exec_v1` برای تست و Git؛ اگر کنترل‌ها اجازه ندهند، به GitHub connector برگرد. این مسیر نباید برای نوشتن مستقیم فایل Production استفاده شود.

**اصل اجرایی:** پیچیدگی تأییدهای زیرساختی تنها برای عملیات زیرساختی/بحرانی باقی بماند. ثبت کد در Git همان ثبت کد در Git است.
