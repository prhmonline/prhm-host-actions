# U06 Native Backup — اتصال تأیید مالک به تراکنش محدود (بدون Provider)

**تاریخ ۱۰ نوامبر ۲۰۲۶.** این تغییر، قرارداد اجراییِ بین شواهد امضاشده OIDC و آداپتور بومی بکاپ را فراهم می‌کند؛ **هیچ Executor یا Binding روت روی سرور نصب نمی‌کند**.

## مسیر دقیق

مالک → Workflow محافظت‌شده `honartik-u06-owner-approval-oidc-v1.yml` → بررسی امضای RSA و approval واقعی → انتقال امن X25519 → ثبت one-use با `O_EXCL/fsync` → **هماهنگ‌کننده عملیات ثابت U06** → آداپتور Root نصب‌شده در آینده → بکاپ و بازیابی Native Universal → گزارش مالی/آزمون rollback.

در این زنجیره هیچ Approval/کلید Provider درخواست نمی‌شود. اما یک Workflow GitHub یا boolean ساختگی **به‌تنهایی اختیار روت نمی‌دهد**.

## قرارداد `honartik-u06-owner-native-transaction-v1.cjs`

ورودی فقط یک مدرک OIDC است که **در همین فرایند توسط ماژول امضاسنج** تأیید شده، و یک مجری با ۱۴ قابلیت **ازپیش‌تعریف‌شده** که باید جداگانه در سرور مورداعتماد نصب و ممیزی شود. هیچ پارامتر `command`، `path`، `shell`، `SQL` یا `deploy` از MCP/کاربر پذیرفته نمی‌شود.

ترتیب الزام‌آور: قفل اختصاصی → پیش‌تصویر دقیق (SHA پروفایل و آداپتور، هویت هنرتیک) → شواهد معتبر Node1 → ژورنال برگشتِ پایدار → مصرف غیرقابل‌تکرار تأیید مالک → ایجاد صرفاً حساب بکاپ محدود → `backup_database()` نصب‌شده → `verify_database_restore()` و آزمون مالی کامل → `offsite_required=true` بازگشت‌پذیر → بررسی Postflight → Commit ژورنال.

**رفتار شکست:** هر خطا بعد از شروع جهش می‌تواند Rollback پیش‌تصویر دقیق را فعال کند. اگر آزمون صحت Rollback شکست بخورد، یک خطای بحرانی صادر می‌شود و Recovery Journal باقی می‌ماند. رکورد مصرف تأیید OIDC حتی پس از Rollback حذف نمی‌شود؛ برای تکرار عملیات باید تأیید تازه مالک صادر شود.

## گیت‌های اصلی

- پیش‌تصویر پروفایل: `79783874cb5170eec3dedcc536f713c4567c585e118f881c1035862a7bba8698`
- پیش‌تصویر آداپتور Universal: `d81223e31bde684f83d1b8b3c93a8fdf2bd4797db33159bf681e6d3898ade2a3`
- DB: `honartik_db`، حساب `honartik_universal_backup`@`127.0.0.1`، چهار مجوز `SELECT, SHOW VIEW, TRIGGER, EVENT`، بدون دسترسی نوشتن.
- شواهد از Node1، آزمون `mysqlcheck` تمام جداول، تطبیق تراکنش‌های مالی و مجموع مبلغ، کیف پول و رزرو، سلامت سرویس و قابلیت rollback اجباری.
- Migration قدیمی Yii، انتشار Front/Backend و Apache switch در این عملیات **ممنوع** است.

## اثبات

این Coordinator با Adapter جعلی در محیط CI اجرا شده تا صرفاً **منطق ترتیب اجرا و شکست** قابل‌آزمون باشد؛ این **اثبات دسترسی روت یا صحت آداپتور واقعی نیست**. دوازده آزمون مستقل شامل امضای واقعیِ Synthetic JWT، جلوگیری از اجرای مجوز جعلی، تغییر SHA، نبود Offsite، نبود ژورنال، شکست بکاپ، Rollback، شکست Rollback، عدم تغییر مالی، Replay و منع عملیات نامرتبط هستند.

آزمون‌های اصلی هویت OIDC و انتقال رمزنگاری نیز در [PR #253 ادغام‌شده](https://github.com/prhmonline/prhm-host-actions/pull/253) با **۳۱/۳۱ PASS** انجام شده‌اند.

## آنچه عمداً باقی است

۱. راه‌اندازی **اجرای واقعی Workflow محافظت‌شده** با تأیید مستقیم مالک و تولید یک JWT واقعی GitHub. در API متصل فعلی امکان Dispatch مستقیم همان Workflow وجود ندارد، و از طریق کد یا مدرک مصنوعی نباید Approval را جعل کرد.

۲. نصب نسخه ممیزی‌شده **Native Root adapter مخصوص U06** با ۱۴ متد ازپیش‌تعریف‌شده، بدون API اجرای فرمان دلخواه، و تأیید SHAهای فعلی سرور. این کد فقط هماهنگ‌کننده است، نه درگاه روت.

۳. تست جداگانه تراکنش با قفل، ژورنال `fsync`، `SIGKILL`، rollback واقعی در یک VM ایزوله و سپس نصب محدود با تصمیم صریح مالک. **تا آن زمان اتصال Production برقرار نشده است.**

۴. اجرای Native Backup واقعی با حساب محدود و فایل خصوصی MySQL، فعال‌شدن Offsite و گزارش صحت مالی روی بازیابی ایزوله. این مرحله پس از فراهم‌شدن تأیید مالک به‌صورت مستقل انجام می‌شود.

**وضعیت:** اتصال Source/CI آماده؛ Provider حذف از مسیر توسعه؛ U06 و مجری روت زنده هنوز مسدود و بدون تغییر Production.
