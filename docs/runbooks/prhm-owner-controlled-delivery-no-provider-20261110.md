# PRHM — مسیر مستقیم مالک برای توسعه و انتشار (بدون Provider)

**تصمیم مالک پروژه — ۱۰ نوامبر ۲۰۲۶**

## ۱. توسعه و کدنویسی: Provider حذف است

برای ثبت تغییر در GitHub، رفع باگ، توسعه سایت، تست، PR، مستندسازی، بررسی فقط‌خواندنی سرور، تحقیق و طراحی نیازی به Provider، بوت‌استرپ کلید Provider، ثبت Host Action یا تأیید سطح ۴ نیست. اجرای کار از مخزن درست و با SHA واقعی، آزمون و رعایت دسترسی همان مخزن کافی است. درخواست‌های تکراری برای Provider یا ایجاد Host Action صرفاً برای تغییر کد ممنوع است.

## ۲. انتشار و تغییرات حساس: اختیار با مالک و کنترل فنی

برای عملیات نوشتنی Production مانند ساخت حساب MySQL، تغییر تنظیمات روت، اجرای Migration، انتشار Backend یا Restart سرویس، مسیر هدف **Owner-controlled** است:

- تغییرات از Git و Commit SHA مشخص، همراه CI و بازبینی لازم همان مخزن شروع شوند.
- تأیید عملیاتی توسط مالک در **GitHub Protected Environment** با هویت معتبر و OIDC یا مسیر مدیریتی مستقل و دارای گزارش قابل‌ممیزی انجام شود. گردش‌کار موجود `universal-owner-recovery-oidc-v1.yml` یک نقطه شروع است، ولی **فقط شاهد هویت و تأیید** است و به‌تنهایی مجوز اجرای دستور Root یا جایگزین امضای کنترل‌پلین نصب‌شده نیست.
- Executor فقط عملیات ازپیش‌تعریف‌شده، حداقل دسترسی، snapshot/backup قابل‌بازیابی، احراز محیط هدف، بررسی سلامت و Rollback ثبت‌شده را اجرا کند؛ هیچ اجرای آزاد شل یا تغییر دلخواه DB از طریق ابزار غیرمجاز انجام نشود.
- اگر Registry فعلی فقط نوع خاصی از تأیید را می‌پذیرد، باید **مهاجرت نسخه‌دار و مجاز سیاست/Executor** به سازوکار تأیید مالک انجام شود. صرف تغییر فایل دستورالعمل یا موفقیت CI قفل قدیمی را باز نمی‌کند.
- برای Production حساس (مالی، بلیت، پرداخت) بکاپ و بازیابی واقعی، کنترل مغایرت داده، انتشار با SHA ثابت، Health و Rollback الزامی‌اند؛ تأیید مالک جایگزین این آزمون‌ها نیست.

**Provider approval از استاندارد عملیاتی آینده PRHM کنار گذاشته می‌شود**، نه اینکه کنترل‌های فعلی سرور به‌صورت پنهانی غیرفعال شوند. تا زمان نصب مجاز مسیر Owner، گیت نصب‌شده موجود باید Fail-closed باقی بماند.

## ۳. کار معطل U06 هنرتیک

- شواهد قبلی: بازیابی کامل SQL هنرتیک از Node1، تست حداقل چهار مجوز بکاپ MySQL در Clone، و تست واقعی توابع نصب‌شده Universal روی دیتابیس آزمایشی. اینها جایگزین بکاپ بومی از داده زنده نیستند.
- هدف: تبدیل روش تأیید برای همین اقدام به **مالک → GitHub protected environment / OIDC → Executor محدود → مدرک بکاپ و Offsite**؛ بدون Provider.
- عملیات آینده فقط پس از راستی‌آزمایی مجاز محیط: ساخت حساب بکاپ فقط‌خواندنی `honartik_universal_backup` با دسترسی `SELECT, SHOW VIEW, TRIGGER, EVENT` روی `honartik_db.*` و فایل خصوصی `mysql.cnf`، فعال‌کردن `offsite_required=true` با بازگشت، اجرای `backup_database()` و `verify_database_restore()` در مسیر نصب‌شده، `mysqlcheck` و آزمون یکپارچگی مالی.
- **موارد هنوز انجام‌نشده:** اتصال واقعی تأیید Owner به Executor Root، تأمین اعتبارنامه Production، اجرای Native backup واقعی و فعال‌شدن الزام Offsite. تا آن زمان **U06 باز** و Backend deploy ممنوع است. U05 و U03 نیز موانع مستقلی دارند.

## ۴. وضعیت مسیر قدیمی Provider

[Host Actions Issue #251](https://github.com/prhmonline/prhm-host-actions/issues/251) و [Draft PR #250](https://github.com/prhmonline/prhm-host-actions/pull/250) مربوط به طراحی قبلیِ Provider هستند و در مسیر جدید نباید به‌عنوان پیش‌نیاز توسعه یا شرط اجرای کد معرفی شوند. مسیر Owner مستقلاً از طریق این سیاست و PR جدید پیگیری می‌شود. مستندات تاریخی برای ممیزی باقی می‌مانند؛ الزام Provider برای کارهای توسعه‌ای از روال فعال حذف می‌شود.

## ۵. معیار پایان

- کدنویسی عادی مستقیم با Git و CI کار می‌کند و درخواست Provider تولید نمی‌کند.
- تغییر Production نه با عبارت «Provider تأیید کند» معطل می‌شود و نه با اجرای مخفی Root: تنها با تصمیم قابل‌اثبات مالک و کنترل‌های نصب‌شده و ممیزی‌شده انجام می‌شود.
- موفقیت Git و تست، **Production DONE نیست**. ادعای اجرای واقعی فقط پس از ثبت SHA منتشرشده، Health، بکاپ و Rollback مجاز است.
