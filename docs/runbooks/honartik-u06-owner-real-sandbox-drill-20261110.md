# U06 — آزمون واقعی SIGKILL، بکاپ نصب‌شده و Rollback در محیط ایزوله

**۱۰ نوامبر ۲۰۲۶ — اجراشده روی سرور prhm-production بدون تغییر Production.**

## شواهد تأییدشده

به‌جای ادامه صرف آزمون‌های Mock، دو آزمایش واقعی لینوکس روی همان میزبان اجرا شدند:

**آزمون A: SIGKILL واقعی + ژورنال FSYNC**

اسکریپت `tests/u06/u06_owner_native_crash_recovery_drill.py` در سه وضعیت، فرایند فرزند را واقعاً با `SIGKILL` کشت: بلافاصله پس از پایدارسازی ژورنال؛ پس از جایگزینی اتمیک فایل آزمایشی؛ و هنگام آماده‌سازی بازیابی. در همه موارد بازیابی دقیق پیش‌تصویر با SHA256 و mode `0600` و idempotence پس از اجرای دوم `PASS` شد. تمام فایل‌ها فقط در `TemporaryDirectory` بودند؛ ژورنال آزمایشی هنگام سناریو حفظ و پس از پایان آزمون حذف شد. **این آزمایش MySQL را تغییر نداده و اثبات rollback حساب واقعی MySQL نیست.**

**آزمون B: اتصال واقعی آداپتور Universal به MariaDB ایزوله**

اسکریپت `tests/u06/u06_owner_actual_native_sandbox_e2e.py` فقط ورودی `--isolated-fixture` را می‌پذیرد؛ هیچ `--apply` یا مسیر تغییر Production ندارد.

- اجرای واقعی `backup_database()` و `verify_database_restore()` از کد **نصب‌شده** `/usr/local/libexec/deploy-control/universal/current/universal/adapters/database.py`.
- ساخت MariaDB 10.11 با digest ثابت، `--network=none`، بدون پورت باز؛ اتصال از Unix Socket موقت `localhost` (نه TCP میزبان).
- ساخت حساب آزمایشی فقط روی Clone با `SELECT, SHOW VIEW, TRIGGER, EVENT` برای دیتابیس آزمایشی `honartik_db.*`، ساخت credential آزمایشی با mode `0600`.
- خروجی آداپتور **۳٬۶۰۳ بایت SQL معمولی** (نه gzip) با SHA256 `39c7155a1b1ac43fea9b293acf38552b54a73d41a91d2b90732c10d45abd384b`. این نکته بعد از یک تلاش آزمایشی ناموفق ناشی از فرض اشتباه درباره فرمت gzip اصلاح شد.
- بازیابی مستقل SQL به MariaDB ایزوله دوم، اجرای full `mariadb-check`، بررسی **۳ جدول/۱ FK/۲ تراکنش مجموع ۳۰۰/۱ کیف پول مجموع ۳۰۰/۲ رزرو** → **PASS**. این مقادیر ساختگی‌اند و آمار واقعی هنرتیک نیستند.
- فعال‌سازی `offsite_required=true` فقط در پروفایل آزمایشی و بازگشت بایت‌به‌بایت آن. اجرای دوم با خطای عمدی پس از ایجاد credential، حذف موفق حساب محدود و فایل و Container؛ نتیجه **PASS**.
- در پایان هر دو سناریو، credential، حساب MySQL آزمایشی، کانتینرها و دایرکتوری‌های موقت حذف شدند. SHA256 پروفایل Production در ابتدا و انتهای تست `79783874cb5170eec3dedcc536f713c4567c585e118f881c1035862a7bba8698` بود.

شواهد ماشین‌خوان: `evidence/u06/honartik-20261110-actual-native-sandbox-and-sigkill.json`.

## آنچه این آزمون ثابت نمی‌کند

- هیچ **تأیید OIDC واقعی** در GitHub Protected Environment صادر یا مصرف نشده است.
- مجری محدود U06 به کنترل‌پلین/Root نصب نشده و ژورنال Root Production ایجاد نشده است.
- هنوز حساب `honartik_universal_backup@127.0.0.1` یا فایل خصوصی `/etc/deploy-control/secrets/honartik_back/mysql.cnf` روی دیتابیس زنده ساخته نشده است.
- `offsite_required=false` روی پروفایل Production باقی است.
- آزمون B از دیتابیس ساختگی سه‌جدولی استفاده کرده و جای آزمون کامل روی بکاپ واقعی هنرتیک را نمی‌گیرد؛ بازیابی واقعی Node1 و ۶۹ جدول در گام مستقل U06 پیش‌تر انجام شده است.
- عملیات Migration، Apache، انتشار Backend و پرداخت با این تست تغییری نکرده‌اند.

## مرز عملیاتی باقی‌مانده و تصمیم بعدی

**نیاز به Provider تأییدکننده برای برنامه‌نویسی نداریم.** کد تأیید مستقیم مالک در PRهای ادغام‌شده #253 و #254 موجود است. برای تکمیل U06 باید یک مجری محدود **واقعی** با همان قرارداد، ممیزی‌شده و قابل‌بازگشت، در کنترل‌پلین مجاز نصب شود؛ سپس یک تأیید **واقعی** GitHub OIDC مخصوص U06 روی nonce سرور مصرف شود و اجرای واقعی Native Backup از Production با بررسی مستقل مالی، Wallet و Reserve انجام شود. بدون آن، U06 «مسدود» باقی می‌ماند و انتشار Backend مجاز نیست.

**نکته ممیزی:** Workflow جاری GitHub از یک حساب درخواست‌کننده و یک حساب بازبین با ID متفاوت استفاده می‌کند و `prevent_self_review=true` را الزام می‌کند. باید پیش از آزمون واقعی معلوم باشد این حساب بازبین تحت اختیار مالک است یا وابستگی خارجی ناخواسته؛ هرگز Approval را جعل نکنید یا از محیط محافظت‌شده عبور نکنید. اگر وابستگی خارج از اختیار مالک باشد، مسیر مورد تأیید مالک باید با طراحی جایگزین و کنترل‌های امنیتی متناسب تغییر کند.
